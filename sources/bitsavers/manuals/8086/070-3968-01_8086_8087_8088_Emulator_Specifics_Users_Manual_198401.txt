INTRODUCTION
This supplement is designed to be inserted into Section 7 of the 8550 System
Users Manual (DOS/50 Version 2) or the 8540 System Users Manual. This Emula-
tor Specifics section explains the features of the 8550 and 8540 systems that
are unique to the 8086, 8088, 8086/8087, and 8088/8087 emulators. Throughout
this supplement, the phrase "your System Users Manual" refers to your 8550
System Users Manual or 8540 System Users Manual. The 8086 demonstration run
at the end of this supplement is designed to be used with Section 1, the
Learning Guide of your System Users Manual; the rest of this supplement con-
tains reference material.


GENERAL INFORMATION

Terminology

The 8086/8088 Emulator Processor boards can be used with any of four proto-
type control probes. The various configurations, and the terms used to
describe them throughout this Emulator Specifics supplement are shown in
Table 7K-1.

Emulator Hardware Configuration

In emulation mode O, the prototype control probe is connected to the emulator
your program runs in 8550 or 8540 program memory. In modes 1 and 2, the pro-
totype control probe must be connected to both the emulator and your proto-
type. For instructions on installing your emulator and probe, refer to your
8086/8088 Emulator Processor and Prototype Control Probe Installation Service
Manual.

Microprocessors Supported

The 8086 emulator emulates the Intel 8086, 8086-2 and 8086-4 microprocessors.

The 8088 emulator emulates the Intel 8088 microprocessor.    8088 Prototype
Control Probes with serial numbers B03xxxx and higher support the 8088-2 (8
MHz) microprocessor.   ( 8088 Prototype Control Probes with serial numbers
below B03xxxx can be upgraded to 8 MHz. Contact your Tektronix Service
Representative for details.)
The 8086/8087 emulator emulates the 8086 microprocessors when used with the 5
MHz version of the 8087.
The 8088/8087 emulator emulates the 8088 microprocessors when used with the 5
MHz version of the 8087.

The 8086 and 8088 processors differ only in their data bus width: the 8086
uses either a 16-bit or an 8-bit data bus width, and the 8088 uses an 8-bit
data bus width only.



Emulation Modes
The 808x emulators support emulation modes O, 1, and 2, as described in the
Emulation section of your System Users Manual. The 808x emulators support
service calls (SVCs) in all three modes.



Clock Rate


8086/8088 Emulator. The input frequency of the 8086/8088 emulator clock
(used in emulation mode 0) is 8MHz. The maximum input frequency of the
prototype's clock (used in modes 1 and 2) is 8MHz.

8087 Emulator. The input frequency of the 8087 emulator clock is 5MHz.    The
maximum input frequency of the prototype's clock is 5MHz.


Symbolic Debug

The 808x emulators support the use of symbolic debug. Many displays in this
supplement include symbolic debug information. Refer to the Emulation sec-
tion of your System Users Manual for information on symbolic debug.

Byte/Word Parameter

Several commands offer you the choice of operating on memory on a byte-
oriented or word-oriented basis.    In affected commands, this choice is
represented by the -B or -W parameter. For the 808x emulator, the default
value is -B (Byte).

OPERATING SYSTEM COMMANDS

AL---Allocate Physical Memory
The 808x emulators support the use of the AL (ALlocate) command. However,
memory segment information is not valid. Use the S (Set) command to assign
appropriate values to the segment registers.
The AL command allocates 4K-byte blocks of program memory to logical
addresses used by your program. The 808x emulators support the -F and -S
dash modifiers, which specify fast or slow memory, respectively. The default
condition is fast memory (i.e., no wait states are inserted during program
memory accesses). The -s modifier is used when jumpers P3505 and P7005 have
been set to support it. These jumpers are discussed in the "Jumpers" subsec-
tion later in this supplement. Deallocating memory does not remove the
"slow" designation: the -S modifier remains in effect until changed by a -F
modifier.

Example •. The following commands allocate memory and display the allocations:

     > AL 0 3FFF <CR>
       4 BLOCK(S) ALLOCATED     12 BLOCK(S) FREE
     > AL 8000 -S <CR>
       1 BLOCK(S) ALLOCATED     11 BLOCK(S) .FREE
     > AL <CR>
       00000 - 03FFF
       08000 - 08FFF   S

       5   BLOCK(S) ALLOCATED   11 BLOCK(S) FREE


BK---Set or Display Breakpoint Conditions

The 808x emulators allow you to set up to three breakpoints. These emulators
support "arming" of breakpoints with the -A dash modifier. (When breakpoints
are armed, the breakpoint conditions must occur in sequence. The actual
break, and its trace line, occur only when the final breakpoint condition is
met.)
You can program any of three conditions: BK1 to arm BK2; BK2 to arm BK3; or
BK1 to arm BK2 to arm BK3. To use this arming feature, first program BK1
(for example), then program BK2 and include the -A parameter. To clear the
arming feature, you must clear the breakpoint that contains the -A parameter.
The 808x emulators also allow you to specify Read (RD), Write (WT) Memory (M)
and I/O operations with the BK command.




                                                                             7K-5

Example. The following breakpoints set the emulator to break on any I/O read
that follows a memory write to address 1COFO

       > BK 1 1COFO M WT <CR>
       >BK 2 ,,I RD -A <CR>


                                      NOTE

       Addresses 8, 9, A, and B are the vector that points to an NMI
       (Non-Maskable Interrupt). These addresses are used by the operat-

       at one of these addresses (for example, to test your program's NMI
       routine), any system or user interrupt that occurs will generate a
       break, not just an NMI.

DEAL---Deallocate Physical Memory
The DEAL (DEALlocate) command removes the previous allocation of program
memory. DEAL operates on 4K-byte blocks of program memory. The -A command
modifier deallocates all of program memory. Memory segment information is
not valid with the DEAL command. The DEAL command does not affect the condi-
tions set with the AL command modifiers -F and -s.

Example.   The following commands are an example of AL and DEAL usage:

     > AL 0 3FFF -S <CR>
       4 BLOCK(S) ALLOCATED      12 BLOCK(S) FREE

     > DEAL -A <CR>

     > AL 0 7FFF <CR>
       8 BLOCK(S) ALLOCATED      8 BLOCK(S) FREE

     > AL <CR>
       00000 - 03FFF     S
       04000 - 07FFF
       8   BLOCK(S) ALLOCATED    8 BLOCK(S) FREE

G---Begin Program Execution

The G (Go) command begins program execution. With the 808x emulators, the G
command operates differently than with other emulators: Usually, if you enter
a command like G 1000, the program counter is set to 1000, and execution
begins from there. With the the 808x emulators, the G command uses informa-
tion from the Code Segment (CS) register and Instruction Pointer (IP) to cal-
culate the effective starting address (EA). The EA is calculated as follows:

     EA = IP + (CS*16)


where IP is the value of the address parameter you enter with the G command.
Since the value of the CS register may be changed during program execution,
it is recommended that you set the CS register (using the S command) before
program execution, to ensure that the program starts at the desired address.

                                      NOTE

     The value of the address parameter of the G command must be less
     than 10000H.


MAP---Set or Display Memory Map Assignments

The 808x emulators support the MAP command as described in your System Users
Manual, with the following exceptions:

•    The 808x emulators map memory in 4K-byte blocks.

•    The -M and -A modifiers are not supported.

•    You may not include memory segment information in the MAP command.

default condition is that all prototype memory is available to program.)
Memory segment information is not valid with the MEM command. For an example
of HEM command usage, see the discussion of the NOMEM command.

The RD (ReaD) command reads data from a prototype I/O port. This command

You may include symbolic names as input to the RD command.

Memory-mapped I/O is selected with the -M command modifier. The 808x emula-

SPECIAL CONSIDERATIONS
The following paragraphs describe some of the special considerations of the
808x emulators.

The HALT Instruction

In all three modes, a HALT instruction causes the emulator to halt. Control
does not automatically return to the operating system. Press CTRL-C to
return control to the operating system.

Losing Clock Causes Emulator Fault Error

When you select the 808x emulator, a section of system code is loaded in the
emulator. This code is checked each time you start the emulator. If this
code is corrupted in some way, error 45 "Emulator faulted" will occur, and
you must reselect the emulator.
This error is caused by losing the clock in emulation modes 1 or 2. This may
occur if you turn off your prototype while the development system is in emu-
lation mode 1 or 2. You can avoid this error by changing to emulation mode O
before turning off your prototype.

PROM Programmer Considerations

Due to power supply limitations, the 808x emulators must not be selected
while you are programming a PROM.

Emulating the Execution Bus

Internally, the 8086 and 8088 are each dual processors. Each contains an
Execution Unit (EU) and a Bus Interface Unit (BIU). The Bus Interface Unit
prefetches instructions for the Execution Unit, and interfaces the EU to the
outside world. The BIU communicates with the EU via an "Execution Bus".

The 808x emulators emulate the information on the Execution Bus: this means
that instructions are disassembled and traced accurately. Breakpoints are
generated by information on the Execution Bus.
Viewing the Pre-Fetch Queue

With the 808x emulators, you can use the Trigger Trace Analyzer's DISP com-
mand to view the depth of the pre-fetch queue. This feature tells you how
many bytes remain in the pre-fetch queue after each trace line. When the
queue depth is zero, the Execution Unit waits for the Bus Interface Unit to
fetch the next instruction. You can optimize critical sections of code for
execution speed by knowing when the queue is empty.

Segment Registers
The 8086/8088 microprocessor contains four segment registers: Code Segment
(CS), Data Segment (DS), Stack Segment (SS), and Extra Segment (ES). Each
segment register contains the 16 most significant bits of an 8086/8088 20-bit
address. Addresses are given as a 16-bit offset to the segment base address.

The CSX, DSX, SSX and ESX Symbols.   For convenience, a special symbol has
been created for each of the four memory segments that is 16 times the value
in its associated segment register. For example, the symbol DSX represents a
value 16 times the value of the DS register.
The following example shows a use for the CSX symbol:

Example.  The 8086/8087 /8088 microprocessors create the effective address
(EA) for a symbolic label by adding the current Code Segment (CS) times 16 to
the contents of the Instruction Pointer (IP).
The 808x emulators only know the effective address (EA) of a symbol. How-
ever, the address parameter of the G command is assumed to contain only IP
information. Under certain circumstances --- as when the EA of a symbol is
greater than FFFFH, or the CS is not zero --- the 808x emulator calculates an
IP that is larger than 16 bits, and a truncation error occurs.

But since you can use the EA and the CS to calculate the IP:

     IP = EA - (16*CS)

and the value of CSX is 16*CS, you can avoid truncation errors by subtracting
the CSX symbol in the expression representing the desired address. For exam-
ple:

     > G START-CSX <CR>


The -CSX modifier subtracts the CS value from the EA, thus ensuring that the
IP is no more than 16 bits.

SERVICE CALLS

Service calls (SVCs) enable your program to use many system capabilities of
your 8450, 8550, or 8560.

An SVC is invoked with an 8086/8087 /8088 OUT instruction followed by two
NOPs. The operand of the OUT instruction is indirectly referenced through
register DX whenever the SVC port range is larger than OFFH. (For example,
the default SVC port range of OFFFOH--OFFF7H requires that the DX register be
used.) This instruction sequence directs the system to a specified memory
address called the SRB pointer (which points to an SRB -- a Service Request
Block). The SRB pointer tells the system where to find the data (stored in
the SRB) that tells the system which service to perform. Refer to the Ser-
vice Calls section of your System Users Manual for an explanation of service
calls, service request blocks, and SRB pointers.

Table 7K-5 shows the default addresses for the eight SRB pointers. These
addresses and their associated port values can be altered with the SVC com-
mand to suit your program requirements. See the Command Dictionary section
of your System Users Manual for syntax and use of the SVC command.

SVCs in Modes 1 and 2

The 8086/8088 emulator supports SVCs in all three emulation modes. In all
three modes, use two NOPs following the I/O instruction. This allows time
for the SVC to occur.

                                      NOTE

     In mode 1, only the instruction sequence that calls the SVC may
     reside in prototype memory. The SRB pointers, the SRB, and the
     optional I/O buffer must all reside in program memory.


SRB Format
The 8086/8088 emulator uses the LAS (Large Address Space) format for SRBs and
SRB pointers. This format is described in the Service Calls section of your
System Users Manual.

EXAMINE THE DEMONSTRATION PROGRAM
The demonstration program adds five numbers from a table stored in locations
500--504 in program memory and leaves the sum in register AL. (You will
place values in the table later in this demonstration.) The 8085A emulator
demonstration run in the Learning Guide of your System Users Manual contains
a flowchart that illustrates the steps of the program.

The source code contains two kinds of statements: assembler directives (like
ORG and BYTE) and 8086 assembly language instructions. The assembler direc-
tives are microprocessor-independent and are explained in the 8085A emulator
demonstration run. The 8086 assembly language instructions are discussed in
the following paragraphs.

Set Table Pointer. The MOVW BX,#TABLE instruction loads the address of the
table (500) into register BX. As a result, BX points to the first element of
the table. The label START is used by the END directive to specify that the
MOVW BX,#TABLE instruction is the first to be executed.

Set Pass Counter.   Register ex is used as the pass counter.     The MOVW
CX,#TSIZE instruction moves the value of TSIZE into ex. This step sets the
number of passes to 5.

Clear Accumulator. The XORB AL,AL instruction zeros register AL, so that you
may use AL as the accumulator and start adding numbers from the table into
it.

Add Byte from Table. The ADDB AL,[BX] instruction adds the byte addressed by
BX into the accumulator AL. The label ALOOP represents the address of this
instruction; this label is used by the LOOP instruction.

Point to Next Byte. The INCW BX instruction increments register BX, which
then points to the next byte in the table. For example, BX is initialized to
contain 500H. After the INCW BX instruction is first executed, BX will con-
tain 501, the address of the second element of the table.

Decrement CX and Loop Until CX = Zero. The LOOP ALOOP instruction decrements
register ex, the pass counter. If CX is not yet zero, the program jumps back
to the label ALOOP. If ex is equal to zero, the program proceeds to call the
Exit SVC routine.

Call Exit SVC.    The last four instructions of the program are:

      MOVW DX, flOFFF7H
      OUT DX,AL
      NOP
      NOP


These instructions constitute a service call (SVC) that causes an exit from
the program. For more information on SVCs, refer to the Service Calls dis-
cussion elsewhere in this Emulator Specifics section.

You have assembled, loaded, executed, and monitored the demonstration run

•    P---patches a string of bytes into memory

•    TRA---selects instructions to be traced during program execution

Delete the Demonstration Run Files
Now that you've finished the demonstration run, you can delete the source
file, object file, listing file, and load file. If you're using an 8550, the
source and load files are still available to you on the 8086/8087/8088 emula-
tor installation disk. If you 're using an 8560, remember that once you
delete the source file (asm), there is no way of recovering it.

Delete 8550 Files. If your files are on the 8550, use the following pro-
cedure to delete them. First use the USER command to move from the DEMO
directory back into the directory you were in at the start of the demonstra-
tion. Recall that you marked that directory with the brief name /ROOT.

     > USER /ROOT <CR>
