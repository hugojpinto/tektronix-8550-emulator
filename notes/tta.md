# TTA (Trigger Trace Analyzer): reverse-engineering notes

**Status:** emulated at register level (`-tta`, `emu/src/machine/tta.{h,cpp}`, `am9513.{h,cpp}`), in test mode and in run mode.
- **TTA.TST V1.3A** (on `8550_DIAG.IMD`, Select mode 6) passes **option 0 (all modules 00–60)**, 40 consecutive iterations with ERRORS = 0000. It also passes **option 7 (probe interface) with `-tta probe`**, an inferred fixture.
- **Run mode** follows the 8540's OS/40 TTA software, whose ROMs survive ([tta-os40.md](tta-os40.md)). The 8086 and 80186 diagnostics' TTA interface tests (module 70) pass.
- Usage guide with pictures: [docs/TTA.md](../docs/TTA.md).

**No 8550 software in our collection runs the TTA's commands.** DOS/50 V1.0 (1980) predates the board, and its EVT/BIF/CNT/RTT/DRT drive the RTPA. The TTA commands (AD, DATA, BUS, PRO, QUA, CTR, EVE, COU, BRE, TS, TCLR, ACQ, DISP…) were in later DOS/50 versions, which are lost, and in the 8540's OS/40.
- **OS/40's TTA modules survive** in ROMs 160-1381/1382. They are 2650 code, and DOS/50 V2 used the same modules and hooks. They show how run mode is programmed: which input addresses which comparator RAM, the codes in those RAMs, and the Am9513 sequences ([tta-os40.md](tta-os40.md)).
- **TTA.TST exercises the board's test mode**, in which the 2650 itself is the "bus" being watched.
- **Below:** what TTA.TST establishes, then what run mode adds.

## Sources
- `sources/bitsavers/manuals/tta/`: 070-3761-00 TTA Service (Jan 1983: installation, jumpers, verification; no register detail) and 070-3760-01 Trigger Trace Users (Jan 1984: the functional model).
- **TTA.TST:** dump it from memory after Select mode 6 starts (`-type 31 '2\r' -type 41 '6\r' -dump F`), then `build/dasm s2650 F.8301 0 2000 6000`. Module table: strings at 3235–33BF, error codes 11/MMxx. Module code: 30 at 29FD, 31 at 2AAB, 44 at 2C5C, 45 at 2D08 (stimulus table 2D57), 46 at 2E21 (table 2E79), 50 at 2F71, 60 at 3006, 70 at 30A3. RAM initialisation for the event tests: 31D3.
- Method: run a module alone (`-type 51 'T\r' -type 56 'NN\r'`) with `TEK_TTATRACE=1` (ports, event changes, acquisitions, all with 2650-clock-exact times), read the expected values from the module's code, and test a hypothesis against every module at once.

## Functional model (users manual, 1-2 to 1-3, 2-7 to 2-9)
- **Four trigger channels.** Each is an event comparator plus a programmable counter. Trigger = event AND counter output. A trigger can break the program, clock or gate a counter, and drive a BNC output.
- **Comparator inputs, 64 bits:** 24 address, 16 data, 8 probe, 4 counter outputs, 1 event qualifier, 11 emulator-dependent bus control signals. An event is the AND of the definitions over these groups. Address and data can be single values, values with don't-care digits, **ranges, or "not in range"** (`ad -n 2 500 505`): a lookup RAM per input byte, with relation codes cascaded across bytes, is the natural way to build that, which fits the 2-bit codes below.
- **Acquisition memory:** the last 255 transactions, or selected ones.

## Hardware established from TTA.TST
### Ports
| Port | Use | How established |
|---|---|---|
| 70 | Control. Read: written bits plus C0 (board present). Bit 0: comparators on; writing it 0 clears the event latches (45, 46). Bit 1: RAM select (window + system-RAM inhibit). Bit 2: counter clock (44) and run; writing it 0 clears the arming chain (31). 07 = test mode | modules 00, 20, 30–60 |
| 71 | Bits 7–4: trigger k needs arming by trigger k−1 (4 before 1), one bit per trigger (31). Bit 1: acquire every access instead of only those on which event 4 fires (60) | 31, 60 |
| 72 | Interrupt enables, one per trigger (bits 3–0). A write clears the interrupt request | 50 |
| 73 | Trigger latches 4–1 (low nibble). Set by triggers; the 2650 can write it (module 10 walks it, 30/31 clear it before each test) | 10, 30, 31 |
| 74 | 8-bit read/write register, role unknown | 10 |
| 75 | Acquisition pointer (read): the next sample's index | 60 |
| 76/77 | **AMD Am9513** data/command (MAME's device, generated by `tools/port_am9513.py`) | 40–46 |

### Counter chip wiring
- **X1 = 5 MHz** (J6165 "normal operation", from the 8301's 20 MHz oscillator, which also gives the 2650 its 2 MHz), **gated by port 70 bit 2** in test mode (module 44 toggles 70 between 00 and 04); in run mode it runs while the program does (OS/40's timebases time the program, and it sets 70 bit 0 at each run's start and clears it at the end). Module 44 counts F1 between two writes of port 70 that are 13 116 2650 clocks apart (the 2650 timing of its delay loop) and accepts 32 789–32 791 counts: exactly 2.5 per clock. Module 45's F2–F5 windows (9, 42, 402, 4002 clocks, with BCD scaling for F3–F5) each give 1–2 counts, as they must at 5 MHz. This needs I/O times exact to the 2650 instruction: `tek8301::now_cycles()`.
- **SRC k and GATE k+1 = event k** (k = 1…4) in test mode, as levels. Module 45 programs every counter to count source n and stimulates it: a write to row 10·k (event k) for SRC1–4 and GATE2–5. SRC5, GATE1 and F1 are skipped by the test (their table entries jump over the check). In run mode OS/40 names them: SRC k = event k, GATE k+1 = trigger k (the same as event k in module 45, where the counter outputs are high), SRC5 = port 70 bits 5–4's choice, GATE1 = the acquisition strobe (below).
- **Counter outputs OUT1–4** are the four counter signals of the trigger channels. **Outputs left high-impedance read high** (pull-ups): module 30 programs mode 0B0C (output hi-Z) and requires status FF and triggers = events; after a reset (outputs low) it requires C1 and no triggers. Status bits 7–6 read 1.
- **GATEnA** (DB8–DB12 in 8-bit mode) high, as MAME's device defaults.

### Comparator RAM and events (test mode)
- The RAM window: with port 70 bit 1 and EE = 07 (2650 4000–7FFF window to system-bus C000–FFFF) the TTA RAM answers at system-bus E800–F9FF, CPU pages 68–79. Page 75 is absent, and system RAM is inhibited there too (module 20). **Pages 68–6F: acquisition memory** (8 bytes per sample). **Pages 70–74 and 76–79: comparator RAMs.**
- With port 70 bits 1–0 set, **an access to a comparator page looks up a row in every comparator RAM and latches the four event outputs** until the next such access. Accesses to the acquisition pages clock nothing (module 60 reads them back between samples).
- **The decision function** is the one OS/40's encodings imply ([tta-os40.md](tta-os40.md); `docs/ARCHITECTURE.md` §8): a cascade magnitude comparator over pages 76+k (address bytes 2 and 1), 74 (address byte 0), 72/73-low (data byte 1), 71 (data byte 0), 73-high (probe) and 70 (X and Y bytes). TTA.TST passes with it in full, page 70 included. In TTA.TST's terms:
  - **With port 70 bit 2 set (test mode, 07)** every comparator RAM, both nibbles, is addressed by the 2650's A7–0, which is also how the CPU reads and writes them.
  - **With bit 2 clear (03)** they see the run-mode inputs. With no program running, only the probe is driven (page 73's high nibble, module 70). The other lines read high: module 70 writes junk into page 73 row 00 between its probe tests, and that must not disturb them (inferred: the lines are pulled up).
  - **In test mode the 2650's writes to the comparator pages are only stimuli; the RAMs keep their contents.** Module 31 writes 00, 01, 02… into page 79 row 00 between accesses and expects event 4 every time; module 60 rewrites page 70 row 40 likewise. At 70 = 03 writes land (the 8086 and 80186 diagnostics' module 70 fill the RAMs that way).
  - **Rows TTA.TST uses:** pages 76–79 = F5 make the address depend on page 74's pair alone (pair 00 = match, the "value" encoding); pages 76–79 = 80 make it always true; pages 71/72 = 00 make the data always true; page 73's high nibble enables events per row; page 70 = FF passes X and Y. Evidence, with these codes:
  - module 30 writes rows 10·k after the init 31D3 (page 74 = 00, 54, 51, 45, 15 at rows 00…40, i.e. event k's pair cleared at row 10·k; page 73 = F0, pages 76–79 = F5 (the init at ~0x3243 fills all four) and page 70 = FF at those rows, all else 0) and expects event k alone;
  - module 31 expects all four at row 0 (page 74 = 00);
  - module 46 needs the events to drop at rows 07 and C7, where page 73 is 0;
  - module 70 fills pages 76–79 with 80 and expects events 1 and 3, or 2 and 4, straight from page 73's high nibble (50, A0).
- **Trigger k = event k AND counter k's output.** With port 71 bit (3+k) set, trigger k also needs trigger k−1 on an earlier access (module 31's four sequences E0, D0, B0, 70). Triggers set port 73's latches.
- **Event latches hold across port 70 writes while bit 0 stays 1**, even with the clock (bit 2) stopped: module 46 case 4 leaves all events high, and case 5 (active-low gating) relies on that. Writing bit 0 = 0 clears them (module 45's SRC tests need the rising edge after a RAM initialisation).

### Run mode at register level (8086 diagnostic module 70)
The 8086/8088 diagnostic's TTA interface test (on `8550_DIAG.IMD`, Select mode 17, module 70 at 38E0) is the only code we have that programs run mode by registers. It establishes or suggests:
- **Run mode is port 70 = 01:** comparators on, test bit 2 clear. The test sets everything up with 03 (RAM selected) and reads the acquisitions back with 02.
- **Its setup:**
  - page 73 = 10 in every row (event 1 for any probe value), page 74 = 00, pages 76 = 80 and 70 = 01 (rows x5: 11); other pages 0;
  - port 71 = 03: bit 1 acquires every cycle;
  - port 72 = 91;
  - the Am9513 counter 1 in mode 0502 (count SRC5, TC toggled output, down), loaded with 22 (0016), output cleared (E1), and armed (21).
- **What it expects:** 24 acquisitions, the 22nd of which triggers. Then a break of the program at the emulator board (REASON2 08), with no interrupt to the 2650: INT 29 is "unexpected".
- **Read with OS/40's encodings** ([tta-os40.md](tta-os40.md)), all of it fits:
  - port 70 = 01 selects SRC5 = bus cycles (bits 5–4 = 00);
  - page 70's rows x5 with bit 4 set make event 1 need X = xxx1 0101: OUT1 high (counter 1's toggle, at terminal count), OUT3 high-impedance, the undriven qualifier reading 1;
  - port 72 = 91 is break enable for trigger 1 (bit 0), the run marker (bit 4: the activity byte's bit 0 = 1, under mask 83) and bit 7 (unknown).
- **The break goes to the emulator processor, not to the 2650.** In run mode a trigger with its port 72 bit breaks the program. The Emulator Controller holds its slave and raises INT 29 itself (`tek8301::slave_run`); the 8086 board takes the break as its own (REASON2 08). The board does not interrupt the 2650 directly there, or this test sees INT 29.
- **Counter outputs are sampled before the cycle's counts.** A trigger, and the X byte, see OUT as it was before the cycle's SRC edges. The 8086 test (22 counts) and 186.TST (20) then both break after 0014 with the same rule: the break after the instruction that held the trigger. That needed a one-instruction extra delay for the 80186 when the outputs were taken after the edge. The same order is what makes OS/40's delay, pulse and timeout counters match the manual's Table 5-2 (below).

### Interrupt (module 50)
- **INT 29**, shared with the RTPA (2650 vector 3A), **when a new trigger occurs with its port 72 bit set**. Triggers already latched when the enables are written, and bits the 2650 writes into port 73 (module 10 walks 70/72/73 together), do not interrupt.
- **F2 bit 2 (read active low) shows the TTA's request flip-flop**, which a write to port 72 clears. It is not an Emulator Controller latch. Part 3 of the module enables all four triggers with all latched and expects no request.
- Module 50 halts the 2650 three times with no slave enabled and no F9 write in between. Each HALT must be woken by the Emulator Controller's "halted" interrupt (INT 27), so the 8301 now raises it on every new HALT of the master when no slave is enabled, not only once until F9. DOS/50 always has a slave enabled, and all regressions are unchanged.

### Acquisition (module 60)
- In test mode, an access to a comparator page is acquired when port 71 bit 1 is set, or else when event 4 fires on it (module 60: rows 40 and 30 differ only in event 4 vs 3). It is stored in all eight acquisition pages at the pointer, which then advances (port 75).
- **The acquired byte is the 2650's A7–0 in all eight pages**: module 60 expects 40, or 60, in each of them. In test mode the acquisition inputs evidently come from the same CPU address mux as the comparator RAM addresses.

### Am9513 port fixes (in `tools/port_am9513.py`, marked `[tek8550]`)
- `start()` now also runs MAME's `device_clock_changed()`, which the framework calls after start-up. Without it the F1–F5 timers stay off until a counter mode is rewritten.
- The frequency timers count half X1 clocks: in MAME's "full cycle" mode F1's half period is 1/2 X1 clock, which rounded to 0 and stopped F1.
- Level-gated modes take the current GATE level as soon as a counter's mode is written. On the chip gating is combinational, while MAME re-evaluates it only on pin changes, so a counter reprogrammed from active-high to active-low gating kept counting (module 46).
- `counter_mode(c)`: a read-only accessor, so the board can model the pull-ups on high-impedance outputs.
- **Master reset (FF) disarms every counter.** TTA.TST issues FF, then "disarm and save" (9F), and expects counters 2–5 to hold 0000 (module 44). Counters the TTA software left armed (OS/40 arms them at every GO) must stop at FF; MAME's `master_reset` left them counting F1 under the reset mode 0B00.

## Run mode in the emulator
How run mode works, and how the emulator models it, is in `docs/ARCHITECTURE.md` §8; the user's guide is `docs/TTA.md`. The commands (`system/tta_console.*`, standing in for the later DOS/50) program the board at register level as OS/40 does. Facts found while building it:
- **The users manual's timebases are the Am9513's F1–F5** at 5 MHz with decade (BCD) scaling: 200 ns, 2 µs, 20 µs, 200 µs and 2 ms. This confirms the X1 clock found from module 44.
- **`cons` is port 71's arming.** Module 31's "trigger N arms N+1" on successive accesses is the users manual's consecutive-event function: a linked trigger fires only if the previous one fired on the preceding cycle of the kind port 71 bits 3–2 select (OS/40 CONS).
- **An undefined event is always true** (users manual 3-4, 3-9; OS/40's cleared codes). With an unprogrammed counter (output high), a trigger then fires on every cycle; that is how a counter alone can stop a program.
- **OS/40's counter sequences and Table 5-2.** COU and TTA2 load a delay, pulse or timeout counter with v − 1 and set its starting toggle. The Am9513 reaches terminal count on the (v − 1)th count and toggles its output when that TC ends, at the v-th. With the outputs sampled before each cycle's counts, the manual's examples come out:
  - "asserted after the fourth occurrence of event 1" (`cou 2 v=4 s=ev1 o=delay`);
  - pulse high at the v-th count, delay after it, timeout up to it (OS/40 manual Table 5-2);
  - for v = 1 and 2 the sequence steps the counter instead, with the same result.
  - At the end of a run OS/40 reads the counters back (7480) and shows a down-counter as the count still to go + 1, or 0 once done.
- **Acquisition with `acq ev4` after `cons … 34`** also keeps the cycle that armed trigger 4. The users manual's Display 1-14 lists each ADD M fetch before its operand read, and the text says only event 4's transactions are recorded. Storing the arming cycle with the trigger 4 cycle is the only reading that gives that display. *Inferred*; nothing else depends on it.
- **The qualifier input, undriven, reads 1** (8086 module 70, above); the probe lines, with nothing clipped on, read 0 (the users manual's displays).
- **SRC5 = EMUCLK** counts the emulator clock divided by two (users manual 3-8; inferred).
- **DOS/50 V1.0 and INT 29.** Its GO handler at overlay address 681E reads F2, then the RTPA status C2, then E3. It handles the break only if C2 shows "present and stopped"; with C2 = 00 it dismisses the interrupt and keeps waiting. It names the trigger only when its own `BIF` settings agree. The emulator therefore shows a TTA break at C2 when no RTPA is fitted (a bridge, documented as such) and sets E3 bit 4 while the TTA holds the processor (hardware: the hold is SLV OPREQ, as for the RTPA).
- **The manual's 8085 sample program is valid Z80 code**, byte for byte (LXI H = LD HL, ADD M = ADD A,(HL), JNZ = JP NZ…). The tutorial runs it on the Z80 board, and ends the program with `JR $` and `BK` (the exit SVC works too since 2026-11-11, below).
- **A Z80 `HALT` ending a `GO 100` run** stops with `<BREAK     HALT>` every time, with or without `-tta` (re-checked 2026-11-11 with three runs in a row; an earlier build came back at PC 0089 on the second run).

### Checked beyond the tutorial (2026-11-11)
- **Emulation modes 1 and 2** with `tools/proto_target.py` over a Unix socket. Mode 1: an `OUT (10H),A` from program memory reached the target (it printed 0F) and the TTA caught it as `I WT` at 0F10, with A in the upper address byte as on a real Z80. Mode 2: the program and table were patched into the target's RAM (`MAP URW 0 0FFF`, `P` goes through PUT) and ran from there; `data 3 86`, `bus 4 m rd`, `cons cyc 34`, `acq ev4` recorded the five operands. 93 link requests in all.
- **The 8085 board** (`-ep 8085`, 8085 support installed from 062-4641-03): `disp` reproduces the manual's Display 1-2, including the not-taken `JNZ` skipping 010B and `00F7F7 0F I WT`. Like the Z80 support, DOS/50's 8085 GO handler names a TTA stop's trigger only after `BIF 1`/`BIF 2` (C2's bits), so the console prints the cause first. Its 8085 trace-line columns are `LOC  INST   MNEM  OPER      SP     F   A  B  C  D  E  H  L IM SOD`. The code-timing recipe gives 255 × 200 ns = 51.0 µs against 153 states at 3 MHz, exactly.
- **User SVCs work under DOS/50 V1.0 since 2026-11-11, on both boards.** I/O and exit both hung because the emulator held a board stopped by an SVC until the next F9 write. DOS/50 takes the SVC interrupt and services I/O requests while the program runs on, past the `NOP` the Specifics manuals require after the `OUT`. The hold now ends when the 2650 takes the SVC interrupt, or at an F9 write. The Z80 diagnostic's test of the hold (07/0070, eight SVCs in a row, only SVC 1 seen) leaves the interrupts pending, so it still passes. One rule now covers every slave: the Language Processor already resumed when its SVC was taken.
  - **Verified** with the Z80 Specifics' SVC demonstration pattern on both boards: assign `CONO` to channel 0 (status 00), write "HELLO" (printed, 6 bytes), read a typed line from `CONI` (9 bytes) and write it back, then exit.
  - **In V1.0, exit (1A) stops the program like a break:** DOS/50 single-steps the `NOP`, prints its trace line and `<BREAK   >`. Abort (1F) ends it at once.
- **DOS/50 V1.0's SVC functions** (overlay loaded by `SVC ON`, handler 7BB0–7C30, checks at 68FC–6965):
  - **rejected** with status 17: 00, 08, 0A, 0B, 0C, 0F, 1D, 1E, 20, 23, 28, 29, 2A, 3D (table at 6A5A);
  - **with a file name:** 13 and 1C;
  - **special cases:** 14/15 and 17/57;
  - **exit** 1A (flag 6D1D bit 1), **abort** 1F, and 19;
  - **everything else** (10 assign, 01 read, 02 write ...) goes through the general path. The handler marks the block in progress (status 7F), copies it with the DMA routine (vector 1FE0 = 5F47) and polls for completion as a coroutine (7E0B, 69D4).

### Checked against TNIX's TTA help (2026-11-11)
TNIX 2.0, the 8560's Unix, drove the TTA in 8540 integration units with the same command set. Its update disc `TNIX_2.0_UPD-2.IMD` (bitsavers `bits/Tektronix/8560/`) carries the TTA menu script (`usr/lib/ksh/scripts/tta`, "Version 0.0 08JUN83"), with help text and the exact commands each menu issues. Against it:
- **Bus symbols, now established.** For every processor except the 8086/8087, Z8001/2 and 68000, the script lists the generic set: "f fetch, nf not a fetch, m memory access, i input/output access (if processor supports IO ports), rd read operation, wt write operation… TTA detects simultaneous occurrences of listed bus signals. For example, b=m rd". That is exactly what the emulator uses for the Z80 and 8085 boards. The 8086's own set is recorded in `notes/8301.md`.
- **Events and triggers.** "Events are tested and cleared on every processor cycle, while triggers are not cleared until the trigger condition is false. For example, if the event is the occurrence of the data byte 00, and 3 consecutive 00 occur, there will be 3 events and 1 trigger seen." Counting already followed this (`s=evN` per cycle, `s=trigN` per occurrence). **Breaks did not:** a stop or continue acted on every instruction during which the trigger was true. It now acts on the trigger's occurrence (its rising edge). Checked with three NOPs (00) fetched in a row, `eve 1 d=00 b=f`, `cou 2 v=0 o=arm s=ev1`, `cou 3 v=0 o=arm s=trig1`, `bre 1 cont`: counter 2 = 3, counter 3 = 1, and one trace line.
- **The menus' recipes run unchanged.**
  - "time code": `tclr 1 2`, `eve 1 a=start`, `eve -s 2 a=end`, `cou 2 clr v=0 o=arm g=seqh s=unit`. On the sample program (0100 to 010C) it reads 210 × 200 ns = 42.0 µs: 156 T-states of program plus the 12-T `JR` in which the break lands, at 4 MHz.
  - The others: "count events" (`cou n clr s=evN`), "until bkpt" (`cou n clr v=0 o=arm s=…`), "while true" (`g=trigh` on counter N+1), "after trigger" (`g=seqh`), "trace prgm" (`eve -c n clr a=start end`) and "bkpt" (`eve -s n clr a=…` / `d=…`).
- **Counter limits:** "a current counter value of 0 may indicate … event 1 never occurred … 65535 indicates that the source clock is too small". OS/40 reloads up-counters with FFFE, and they count once, so they stop at the top.
- **`disp`:** "current" (since the last start/stop: the samples carrying the current run marker, as OS/40's DISP finds them), "all 255" (`-a`), "last n".

## Open
- **Run mode, not established by any code we have:** port 74 (the 8086 diagnostic writes 75 to it; OS/40 never touches it), port 71 bit 0, port 72 bits 5–7, bit 4 of pages 76–79, and page 68 bits 4–1 of the acquisition record (bit 4 taken as the qualifier). See [tta-os40.md](tta-os40.md) §5.
- **The probe and the qualifier** have no source. A faithful one would be a separate Data Acquisition Interface connection, as the real P6451 probe was a separate cable from the emulator's probe (see the proposal in the session notes / ROADMAP), not more bits on the prototype link.
- **The probe fixture's polarity.** Module 70 (option 7, code at 30A3–3194) asks for "the set-up procedure described in the Probe Interface Test section of the TTA service manual", which our 070-3761-00 lacks. What the code shows:
  - Set-up: it programs the counters hi-Z, sets 72 = 90, 71 = 02 (acquire every access) and 70 = 02, clears pages 68–73, fills pages 76–79 with 80 and page 70 with FF, and writes 50 at page 73 row 55 and A0 at row AA. Then 70 = 03.
  - The test writes AA, then 55, to Emulator Controller port F4: the extended address A23–A16, written active low. After each write it touches page 73 and expects port 73 = 5, then A. It clears 73 in between.
  - On failure it prints the probe byte that was acquired, taken from acquisition page 6A at pointer − 2, against the expected one. So the third acquisition byte is the probe byte.
  - `-tta probe` models the fixture as the probe on the extended address lines, i.e. probe = ~F4. With it, 55 addresses row 55 → 50 → events 1, 3 = 5. **Inferred:** the probe seeing F4 uninverted, with the high nibble's event bits in reverse order, explains the test equally well.
