# 8301 MDU — hardware notes (from 070-2976-01 §1, §3, §7, §9, §16 + ROM disassembly)

System processor: Signetics 2650A-1 on the System Controller board. FAST clock 2 MHz (J5704), SLOW 1.25 MHz.
The 2650 sees 32 KB (A0–A14); the system bus is 64 KB (BA0–BA15) for system memory and program memory separately.

## CPU address space
| CPU addr | Maps to |
|---|---|
| 0000–07FF | **Boot ROM** 160-0728-01 when EA<5> = 0 (enabled by RESET) |
| 0000–0FFF | **Diag ROM** 160-0802-01 when EA<6> = 1 (overrides boot ROM) |
| 0000–1FFF | System RAM 0000–1FFF |
| 2000–3FFF | System RAM page (D3<7:5>)·2000. Power-up D3 = 0 → page 0 (alias!). The boot ROM writes D3 = 20 for identity |
| 4000–7FFF | 16 KB window: EE<2> = 1 system / 0 program memory, EE<1:0> = BA15:14 block. EE<3> = MAPEN. The boot ROM writes EE = 05 → system 4000–7FFF (linear 32 KB) |

The memory map / write-protect RAM sits at system-bus FE00–FFFF (bits D0/D2): 512 blocks of 128 B.
Both ROMs start with interleaved 2-byte vector pointers that also execute harmlessly (e.g. diag `00 81 00 87 …`).

## Boot flow (from ROM disassembly)
- RESET → boot ROM at 0000. It reads ED: switch 6 open → CFM/diag; else it checks the self-test state and normally enters the diag ROM (07e5: EA = 60, jump 05ac).
- ROM hand-over works by overlapping code at 07ec–07f9. In the diag ROM: `EA = 00` → the next fetch comes from the boot ROM (07f0 `bcta 0020` / 07f7 `bcta 05ac`).
- Boot init: ACIA master reset (03 → CE/CC/CA), terminal ACIA control 15, E9 = 0, EE = 05, D3 = 20, LEDs.
- OS hand-off: it copies `lodi 20; wrte ea; bcta *1819` to RAM 1800, so the boot ROM is unmapped and it jumps via the pointer at 1819.
- It programs DMA ch2 (94/95) and E9 = A0 for HSI transfers. Strings: "BOOT V2.1", "no boot file", "comm error?", "/KERNL", "8301/RESIDENT", "/DIAGS/EXEC".

## HSI protocol (observed between the real firmware/OS images in the emulator)
- Packets: `81 | 00 | len | 00 | 00 | a | 00 | b | checksum`, answered with `06` (ACK) or `15` (NAK). `02 … 03` frames carry data (e.g. `02 ff 05 00 00 0b 00 00 "8501 V1.0\n\r" 03`). `19` precedes requests.
- The 8301 boot ROM uses programmed I/O only. It sends a byte when E9 shows TBRE and CTS (mask 0x82). It sends a lone `00` when idle and TBRE.
- **Flow control is per byte:** the 8501 I/O board raises NCTS (RCSR<0>) on start-bit detect and clears it when RBUF is read (by the program or by DMA). The 8501 OS also sets NCTS itself before arming a receive DMA; the DMA then first drains the byte already waiting in RBUF.
- 8501 I/O board CSR<1> = 1 means **OUT** (from memory). The manual's wording is ambiguous; the OS behaviour settles it.
- Boot sequence seen: version message "8501 V1.0" → open `/VOL` → `SYSTEM` directory → `/VOL/SYSTEM/8301/RESIDENT` → ~100 KB loaded → banner **"DOS/50 V1.0   18-AUG-80"**.

## After the banner: Language Processor probe
DOS/50 (code at 6586) disables program-memory relocation (B8/B9 = 50) and writes the Z80 program `06 00 10 fe 76 76 76 76` (LD B,0; DJNZ $; HALT) to program memory 0000. It writes F9 = FA (debug command), clears ports E0–E5 / A0–A5 (optional boards), sets C3/C4/C6, E7 = 80 (Language Processor active), then **HALTs the 2650**.
The "emulator halted" interrupt (vector 36 → handler 681e) reads F2 (active-low pending bits; D4 = emulator halt) and sets 6d1d<4>. The loop retries until it sees it. ⇒ The Language Processor (Z80) and the Emulator Controller's halt detection are required to get past the banner.

## Language Processor / Emulator Controller (as implemented)
- The Z80 (LP) runs from program memory only while the 2650 is HALTed and E7<7> = 1. Any interrupt that wakes the 2650 stops it (master/slave; one CPU on the bus at a time).
- F9 write: D0 = 0 forced reset (Z80 PC = 0, clears pending), D2 = 0 forced jump (PC ← FB:FA), D3 = 1 debug interrupts enabled, D4 = 1 SVC enable.
- SVC n = Z80 `OUT (F8h−n),A` + NOP, for n = 1…8 (ports F7…F0; block relocatable via F3). It raises 2650 interrupt 15+n (vectors 20…2E). The SRB pointer for SVC n is at program memory 40h + 2(n−1) (SAS format).
- Z80 HALT → "slave halted", F2<4> (read active low), interrupt 27 (vector 36).
- Program↔system memory copies for SRBs use 8257 ch0 → ch1 with E9<0>/<6> selecting the source/destination memory.
- Editors and assemblers (EDIT, ASM) are Z80 programs that run on the LP and talk to DOS/50 through SVCs.

## Validated against the 8550 Disk-Resident Diagnostic System 2.4 (062-5412-08)
With `tek8550 -pm ext`, Automatic System Verification passes with zero errors: System Processor & I/O 1.4, Memory 1.4, Language Processor 1.2 (all 14 modules incl. Emulator Controller SVC/single-cycle/BP1/BP2), DMU 1.2 (1000+ s device interaction). RTPA/MAC/TTA are correctly reported absent.
Diagnostic System 3.0 (062-5412-10, `8550_DIAG.IMD`) also passes with `-pm ext`, re-checked on 2026-11-11 after the prototype-link v2 core change; it no longer stops after BOOT V2.1. Screenshots: `docs/screenshots/diagnostics/`.
Facts established on the way (beyond the manual):
- Unmapped I/O ports read **00**; the diag configuration probe treats 00 as "board absent".
- When the 2650 HALTs and **no slave is enabled** (E7<7> = 0), the Emulator Controller reports "slave halted" at once (as described under the Processor Inactive Test).
- Emulator Controller events: SVC immediate; BP1 > BP2 > single-cycle > halt are issued after the instruction ("at the next fetch"). The slave is paused while one is outstanding; an F9 write releases it. F8 bits are active low (0 = enable).
- **Breakpoint registers FC–FF (and F6/F7) are loaded active-low.** PC next/last read back true.
- **F4 (extended bank) is active low:** the diag sweeps FF, FE, … and FF selects bank 00. The program-memory boards are strapped at bank 00. The 8257 DMA and the Language Processor do not use F4.
- **Two program-memory board generations:** DOS/50 V1.0 (1980) writes F4 = 00 and B8 = 10, which only works on boards **without** the extended comparator (default). The 1981+ boards with the comparator (B8/B9 D6) are needed by the 1983 diag (`-pm ext`).
- **SENSE input** carries a ~25 Hz square wave (20 ms half period), used by the processor-speed test (expects "2 MHz").
- 2650 timing: a taken RETC costs no extra cycles (MAME adds 2); the interval-timer test requires the corrected timing.
- Parity interrupt (vector 1) and the error-address latch stay set until D2 is read (first error wins).
- 8501: the LSI-11 budget is 3.1 M T11 units/s, calibrated with the disk LTC test's 1-second loop (28100 × 108 units).

## Z80 emulator processor board (8300E04) -- reverse-engineered from DOS/50 V1.0
No service manual (070-2715) or firmware dump survives. The OS/40 manual says that in mode 0 the Z80A "mobile microprocessor" (BC-5940-01: Z80A CPU + 3 TTL) plugs straight into the emulator board. Behaviour inferred from DOS/50's GO/BK/TRACE code (2650 routines 6e55, 7138, 7159):
- **E3** = emulator board control. Bit 7 = run/enable as slave (DOS/50 writes 80 to start, 92 when stopped). Reading E3 gives status; DOS/50 tests bit 4. The other bits are below ("E3 write bits").
- **Jump-address registers FA/FB/F5 are active-low**, like the breakpoint registers: FB:FA = FEFF starts the user program at 0100.
- **Register block:** DOS/50 swaps program memory 0000–001A with its saved context (routine 7159) around every board-firmware call. Layout: 0 IM, 1 IFF1<7>/IFF2<6>, 2 R, 3 I, 4–11 L' H' E' D' C' B' A' F', 12–13 IY, 14–15 IX, 16–23 L H E D C B A F, 24–25 SP, 26 see below. PC is not in the block: it goes through the forced jump on start and comes from the PC-next latch on a break.
- **Block byte 26 = how the dump entry is reached.** DOS/50 writes it, the firmware only receives it. Before every dump (F809), DOS/50 V1.0 at 6DF3–6E07 clears context byte 26 (system memory 6DD1). If the program stopped at a HALT (6D20 bit 4, set from the "emulator halted" interrupt by 681A/7C64), it sets byte 26 = **02** and clears F9 D1. The dump is then forced with **F9 = F9** (forced jump plus forced interrupt, the Z80's NMI) instead of FB. Reason, inferred: a halted Z80 runs internal NOPs and doesn't fetch, so a forced jump alone can't reach it. The NMI wakes it but pushes the PC and clears IFF1, and byte 26 tells the firmware to undo that. Nothing in DOS/50 reads byte 26 back. Z80 diag E1 doesn't compare it either (its expected table, 3569, covers bytes 12–25). Seen with `TEK_EPTRACE` (`PATCH 100 3E 55 00 76`, `GO 100`): the dump entry shows block byte 26 = 02 and F9 = F9. *Emulator:* the high-level dump absorbs that forced NMI. Before 2026-11-11 it stayed pending and fired on the next `GO`, which sent a program resumed after a HALT break to 0066.
- **Firmware entries** (on the board, top of the Z80 address space; reached by forced jump written FF:07F9 / FF:07F6):
  - **F806 restore:** load all registers from the block, then signal with an SVC. DOS/50 7138 halts and waits for any SVC; a HALT instead gives error 45 "Emulator faulted".
  - **F809 dump:** store all registers into the block, then SVC.
- **Start sequence:** restore (F806) → SVC → DOS/50 swaps memory back, E3 = 92 → forced jump to the user PC (E3 = 80).
- **Stop sequence:** break (BP1/2, single cycle, ESC ESC) → E3 = 80, forced jump to F809 → SVC → registers displayed.
- Emulated at high level in `epz80_board::firmware` (`emu/src/machine/epz80.cpp`). Verified: GO, BK + break display, DS, GO again with registers preserved, TRACE ALL (single-cycle), ESC ESC break.
- **E3 write bits** (established 2026-11-11 from every E3 value DOS/50 V1.0 and Z80.TST write). DOS/50 keeps the run value in 6D29. 6D3A holds the board's port (E3; E7 for the LP, and the 8085 support uses E5), patched into the WRTE/REDE instructions (616E, 685A).
  | Value | Written by | Situation |
  |---|---|---|
  | 00 | DOS/50 65B9, diag | board off/reset; diag test 10 "emulator inactive" |
  | 7F | DOS/50 617E | board deselected |
  | 92 / B2 / F2 | DOS/50 (6D29) | user program, mode 0 / 1 / 2 |
  | 80 / C0 | DOS/50 6E0D–6E18, 6E7E–6E89 | dump/restore firmware call, mode 0 / modes 1–2 |
  | C0 | DOS/50 71BF | GET/PUT firmware call (prototype memory, modes 1–2 only) |
  | 96 | Z80.TST descriptors | every user-code test (00–C0) |
  | 94 | Z80.TST D0/E0 descriptors | **E0/E1 run the firmware dump F809 with E3 = 94** |
  | 80 | Z80.TST 347A | D0: the 2650 checksums the PROM |
  | 86 | Z80.TST 2F3E | test 40 set-up: forced jump onto a HALT in user memory |

  - **Bits 6–5 = emulation mode:** 00 mode 0, 01 mode 1, 11 mode 2. The EM overlay (DOS/50 665E–6681) builds them as 20 for mode 1 and 60 for mode 2, ANDs 6D29 with 9F and ORs them in. EM 1 and EM 2 turn 6D29 into B2 and F2; checked with `-dump`. Firmware calls set bit 6 whenever bits 6–5 ≠ 0. The emulator's `prototype_mode()`/`prototype_all()` already decode these bits.
  - **Bit 1 = 0 maps the firmware PROM for the Z80.** Every firmware run has it clear: DOS/50's 80 and C0, and the diag's 94 in E0/E1, where the forced jump to F809 must execute PROM code because program memory there holds only the fill byte. Every user run has it set: 92, B2, F2, 96, and 86, where the Z80 executes the HALT at FFFF from program memory. *Inferred:* the 2650's view of the PROM (diag D0 reads it at F800–F9FF with E3 = 80) uses the same bit, since no code tells bit 1 and bit 4 apart there. The 8080, 8085 and 6800 diagnostics on the same disc follow the pattern too: 96 for user tests, 80 for both PROM tests. The 8048 test's 82 belongs to a different board design. *Emulator (2026-11-11):* the PROM answers, and a forced jump into F800–F9FF enters the firmware, only while E3<7> = 1 and E3<1> = 0. A `GO` into F800–F9FF from DOS/50 (92) now runs user code.
  - **Bit 4: not settled.** DOS/50 clears it for every firmware call and sets it for every user run, so it marks firmware versus user. It doesn't gate execution, though: the diag runs the firmware with it set (94) and user code with it clear (86). Possible meanings (none confirmed): gating prototype interrupts or the analyzers' qualifier during firmware runs. The OS/40 Z80 Specifics say "Interrupts are detected only when user code is being executed" (070-3939, 7C). Pinning it down needs the firmware PROM or the board schematic (070-2715, not found). The emulator ignores it.
  - **Bit 2:** only the diagnostic sets it (96, 94, 86); DOS/50 V1.0 never does. Meaning unknown; ignored.
  - **Read side:** DOS/50 V1.0 reads only bit 4 (halted, 685A). The diag reads bit 5 (present, configuration probe 4454) and stores the rest at 2528 without comparing it. Reads 20 | 10 (halted), as emulated, agree with everything that is checked.

### Validated against the Z80 emulator diagnostic (Z80.TST V1.1, on the 3.0 diagnostic disk)
Select mode, test 9. Everything passes except **07/00D0**, the PROM checksum, which needs the original firmware. Facts the test established:
- **E3 read bit 5 = board present.** This is the board ID the diagnostic configuration probe tests; bit 4 = halted, as before.
- **F9 D1 = 0: forced interrupt.** On the Z80 board this drives the CPU's **NMI**, which also wakes it from HALT. The test forces a jump onto a HALT, forces the interrupt, and expects PC 0066 followed by "emulator halted" (07/0040).
- **An SVC holds the emulator processor until the 2650 takes the SVC interrupt or writes F9.** With eight `OUT (F7…F0)` in a row and the interrupt left pending, only SVC 1 may be seen. A breakpoint on the same instruction is pending as well, e.g. INTERRUPT = 0801 = BP1 + SVC 1 (07/0070–0075). The Language Processor resumes the same way, as soon as the SVC is taken: DOS/50 tools rely on that, and so do user programs' I/O SVCs under DOS/50 (`notes/tta.md`).
- **The firmware answers with the debug SVCs:** dump/restore (F806/F809) → SVC 7 = "Debug SVC 1", interrupt 22; get/put (F800/F803) → SVC 8 = "Debug SVC 2", interrupt 23 (8301 interrupt table; 07/00E1). DOS/50 accepts any SVC there.
- **Firmware PROM: 512 bytes at F800–F9FF of program memory** while E3<7> = 1 and E3<1> = 0 (firmware mode; until 2026-11-11 this note said E3<4>, see "E3 write bits"). The 2650 reads it through the bank window (EE = 03, 7800–79FF). The checksum adds each byte into a 16-bit sum, then rotates both bytes left through carry; the expected value is **0852**. Not dumped. The PROM reads FF unless you pass `-ep-prom FILE`. `-ep none` removes the board (the configuration before 2026-11-12, in which Automatic verification passes).
- **Result word of the emulator diagnostics** ("INTERRUPT = hhll"): hh = debug interrupts (08 BP1, 04 BP2, 02 single cycle, 01 emulator halted; 10 = timeout, nothing arrived), ll = one bit per SVC 1–8.

## 8085 emulator processor board (8300E06) — reverse-engineered, validated by 8085.TST V1.1
- **Selection:** `-ep 8085` fits it in place of the Z80 board. CPU: MAME's i8085 core, ported like the others (`emu/src/cpu/i8085`). It passes TST8080 and 8080PRE. CPUTEST stops on the 8080's always-1 flag bit, which is the 8085's overflow flag.
- **Control port E5** (as E3 on the Z80 board): 80 = firmware call, 92 = run (mode 0). Reading gives bit 4 = halted, bit 0 = SOD, bits 7–6 = RST 6.5/5.5 (below). 8085.TST writes 96 for user tests and 80 for both PROM tests; the configuration probe writes 86. It never separates bit 4 from bit 1, so for this board both are only known to be 0 in firmware mode.
- **Firmware** (not dumped; emulated at high level): a PROM mirrored through F800–FBFF, visible in program memory in firmware mode. Entries are decoded by their low byte: **EA restore**, **ED dump**. DOS/50 calls FBEA/FBED or FAEA/FAED; the diagnostic calls F8ED.
- **Register block:** 14 bytes at program memory 0000–000D, found by filling the dump with marker bytes and reading `DS`:
  - 0 L, 1 H, 2 E, 3 D, 4 C, 5 B, 6 A, 7 F;
  - 8 not used by DOS/50 (see below);
  - 9–10 SP;
  - 11 RIM value (SID 80, I7.5 pending 40, IE 08);
  - 12 SIM masks in bits 2–0 (1 = masked; `DS` shows them as M7/M6/M5);
  - 13 the **E5 status**, which DOS/50 writes after every dump (see below).

  DOS/50's initial context has 11 = 07 and 12 = 0F. The PC isn't in the block.
- **Byte 13 = E5 read, stored by DOS/50.** After each dump, the 8085 support (`/8301/8085/MONITORS`, resident at 6E3D–6E51 in V1, same code at file offset 2C3 in VERSION2) reads E5 into context byte 13 (6DC4). It ANDs the firmware's RIM byte 11 with CF, then ORs in 20 if E5 bit 7 is set and 10 if E5 bit 6 is set. `DS` (7799–77DD) prints byte 13 bit 0 as **SOD**, and ORs byte 13 bits 7–6, shifted right by 2, into the RIM value it shows as I6/I5. So **E5 read: bit 7 = RST 6.5, bit 6 = RST 5.5** (the prototype's input pins, as the board sees them; latched or live is not known), **bit 0 = SOD** (the 8085's serial output, which RIM can't read back), and bit 4 = halted. *Emulator (2026-11-11):* E5 bit 0 returns the core's SOD line. `PATCH 100 3E C0 30 76`, `GO 100`, `DS` now shows SOD=1. RST 5.5/6.5 read 0, since they come only from a prototype and the 8085 has no modes 1–2 here.
- **Restore entry FBEA versus FAEA = the IE bit.** DOS/50 6EE2–6EED forces the restore at FB:FA = 04:15 active low (FBEA), or at 05:15 (FAEA) when context byte 11 bit 3 (IE) is set. FAEA is presumably the variant that ends with EI. The dump is always FBED.
- **Byte 8: not used by DOS/50.** No code in V1 MONITORS or DS[TAT] reads or writes context byte 8 (6DBF). It is only swapped. DOS/50 leaves it 00, and `DS` doesn't show it. 8085.TST's PROM functional test (expected table at 3503: 56 78 D5 E5 BA C5 AA, then FF wildcards) skips it, as it skips F, SP and RIM. It is probably firmware scratch or padding *(inferred)*; only the PROM would tell.
- **Forced interrupt = TRAP** (to 0024; it also wakes the CPU from HLT). The line is held until an instruction has run, because MAME cancels a TRAP whose line drops first (06/0040).
- **Break mechanism:** DOS/50 enters the dump with **F9 = F9**, a forced jump plus a forced interrupt. The firmware saves the user PC (via TRAP), and the **restore entry resumes there by itself**: during `TRACE` DOS/50 restores without forcing a jump. High level: the jump keeps the CPU's PC as the resume address and consumes the interrupt.
- **Results:** `8085.TST` passes everything except **06/00D0**, the PROM checksum (expected 5716; PROM not dumped). Automatic verification detects the board through the probe (E5 ← 86, forced jump, an interrupt must arrive). In DOS/50 (8085 support installed from the 8085 disk), these all work: ASM (8080/8085 ASM V4.0B), LINK, LOAD, GO, BK, `DS` with the full 8085 state (SIM/RIM), `TRACE ALL`.
- **Not done:** prototype modes 1/2 for the 8085 board, RST 5.5/6.5/7.5 from a target, SOD/SID, block offsets 8 and 13, and get/put (entries E4/E7?).

## PROM programmer (8550F30) interface, as far as known
- **Hardware:** an 8085A controller with its own firmware (not dumped), a five-channel programmable supply and characteristic modules (070-3903).
- **Interface:** ports **D0** (command/control and status) and **D1** (data), plus interrupt 13 (vector 1A).
- **DOS/50 `PSTAT`:** writes D1 ← C0, then D0 ← 17 and D0 ← 0B, then waits for interrupt 13.
- **PROM.TST V1.2:** its first step is "system interface test: master interrupt, command bit, status interrupt, timeout" (error 05/0210).

### Interface (from the DOS/50 driver at 6000–64FF, loaded for the PROM commands, and PROM.TST)
- **D0 write** works as an addressable latch:
  - **bit 3 = 0:** latch Q[bits 2–0] ← bit 4. Only Q7 is used: the command/data flag. 17 = command mode, 07 = data mode.
  - **bit 3 = 1:** pulse bits 2–0. 3 = byte ready for the controller (0B, sent after D1 holds the byte); 4 = reset (0C); 5 = acknowledge interrupt 14 at the controller (0D); 6 = acknowledge interrupt 13 (0E).
- **D0 read** = the status byte posted by the firmware. **D1** = a data latch in each direction.
- **Interrupt 14** (vector 1C, code 16) = status posted. **Interrupt 13** (vector 1A, code 15) = data phase step. On the 8301 both are edge-triggered: PROM.TST never acknowledges them at the controller; DOS/50 does.
- **Status byte:**
  - **bit 0 = OK**, with bits 6–5 = next phase: 60 = controller wants parameters (each int 13 = "send next parameter byte"); 20 = controller accepts data (int 13 = "send next data byte"); 40 = controller sends data (int 13 = "byte in D1"; the host reads it and pulses 0B for the next); 00 = done.
  - **bit 0 clear:** done; bits 1–2 = failure reasons (00 = passed / complete for the self-tests).
  - **bit 7:** unrecognized command ("Unrecognized Command").
  - The host acknowledges *every* status with A0, including the final one, which the controller answers with one int 13 carrying no data. DOS/50's int 13 handler turns that into idle; PROM.TST waits for any interrupt.
- **Conversation:**
  1. The host sends a command byte (command mode, 0B).
  2. The controller posts a status (int 14).
  3. The host answers **A0** in command mode ("proceed").
  4. The controller runs the phase, one int 13 per byte, then posts the next status.

  **B0** ends or aborts. DOS/50 `PSTAT` queues C0, A0, B0.
- **Byte formats** (DOS/50 638B bits 1–0): 0 = byte; 1 = nibble (high or low per bit 2, for 4-bit PROMs).

### Command set (emulated in `emu/src/machine/prom_programmer.cpp`; all 14 PROM.TST options pass)
| Command | Function | Exchange |
|---|---|---|
| AA | interface echo | 61 → 1 parameter → 41 → returns [AA, parameter] → 00 |
| 08 / 18 | characteristic module checksum / module test | 00 complete / 01 executing |
| 28, 30, 40–42, 50, 60 | self-tests: front panel, RAM, ROM all/1/2, 8085 processor, all power-up tests; +4 = firmware looping | 00 complete (01 while looping) |
| 38 | write-PROM diagnostic | 61 → device index → 01 (runs until aborted) |
| 58 | power channel range test | 41 → 10-byte sense records → 01 |
| 70–73 | set channel voltage (parameters: sixteenths<<4, integer volts) | 61 → 2 parameters → 41 → record → 01 |
| 80–84 | evaluation sweep (parameters: status display FF/00, D/A 1, D/A 2) | 61 → 3 parameters → 41 → records → 01 |
| 90–95 | channel control (parameters: mode 01 on+set+sense, 02 on, 04 set, 08 sense, 10 continuous, FF off; D/A) | 61 → 2 parameters → 41 → record → 01 |
| C0 | status: STATUS, FSTAT (fatal), NFSTAT (non-fatal), DSTAT 1–8 | 41 → 11 bytes → 01 |
| D0 | characteristic module information (last byte = number of device types) | 41 → 10 bytes → 01 |
| A0 / B0 | proceed (and acknowledge) / end or abort | — |

**Sense record** (10 bytes): channel (0-based), D/A input, A/D output, expected volts (sixteenths<<4, integer), expected A/D, actual volts (same encoding), supply range, internal channel. Ranges (070-3903 Table 1-2): 4–30 V, 4–30 V, 4–12 V, −5…−25 / −23…−40 V, 5 V fixed.

| D0 | characteristic module information (full layout below) | 41 → n bytes → 01 |
| E0 / E1 | read device (DOS/50 `RPROM`, `CPROM`; E1 = option variant). Parameters: device index (1-based), first address (3 bytes), last address (3 bytes) | 61 → 7 parameters → 41 → data → 01 |
| F0–F3 | program device (DOS/50 `WPROM` sends F2), same parameters | 61 → 7 parameters → 21 → host sends data → 01 (04 = verify failure) |

**Module information:**
1. A 10-byte header: bytes 3–5 = the module's part number 160-xxxx-yy in BCD; byte 9 = number of device types.
2. The device names, each ended by 0D, then FF.
3. A 3-byte maximum address per device.
4. `21` (`!`).
5. A flags byte per device: high nibble nonzero = erased state HI; low bits 01/02/04 = word length 4/8/16.

`PTYPE` prints this; `RPROM`/`WPROM` match the user's type name against it. PROM.TST option 13 reads only the header and ends the transfer with B0.

**DOS/50 command syntax** (PROM software V2.1): `RPROM addr type lo hi`, `WPROM addr type lo hi`, `CPROM addr type lo hi`, `PTYPE`, `PSTAT`. `addr` is program memory and `type` a module device name, e.g. `RPROM 1000 2716 0 7FF`.

### PROM software V2.1 vs DOS/50 V1.0 (`-prom fix`)
The PROM software on the 8550F30 disk (062-6036-01, 1982; `V1.CMDS` for DOS/50 V1) was built for a later DOS/50 V1.x whose resident routines sit 10 bytes higher than in V1.0 (18-AUG-80):

| Routine | Later V1.x | V1.0 |
|---|---|---|
| post event to task | 0304 | 02FA |
| wake the dispatcher | 03DE | 03D4 |

In V1.0, 0304 is the post's inner entry, which needs a message slot from the free list (02CD) in r1. 03DE is the dispatcher's task-entry address table. On a V1.0 system the PROM commands therefore hang after talking to the hardware, whatever the hardware does. `-prom fix` relocates the driver's calls (overlays at 6000–6FFF) whenever the driver writes D0:
- 03DE → 03D4 always.
- 0304 → 02FA (with r1 = r0, which the framework at 6002 stores as its own task id at 60E7) only while a write command (F0–F3) is active.

Status, type, read and compare complete only with the original 0304 call, apparently through state that DOS/50 V1.0 leaves behind. That part is empirical.

**Verified:** `PSTAT` ("NO PROM PROGRAMMER ERRORS DETECTED"), `PTYPE`, `RPROM`, `CPROM`, and `WPROM` alone. **Known issue:** a read or compare after a write in the same session hangs. The device image is correct; restart the emulator.
- **PROM.TST system interface test** (2B75–2D38), an echo through the protocol:
  1. Command AA → status 61.
  2. A0 → int 13 (asks for a parameter).
  3. Data 55 → status 41.
  4. A0 → int 13 with D1 = AA.
  5. Strobe → int 13 with D1 = 55.
  6. Strobe → status 00.

## Boot banner printed twice (genuine ROM behaviour)
The boot ROM prints `BOOT V2.1` at its entry point 0020. It then enables the HSI (0182) and waits.
The 8501 has queued a type `ff 05` message ("8501 V1.0") since power-up. The handler (047c–049f) reads the message, ACKs with `19` and prints the text up to CR. It then does `bcta $0020`, so the whole boot sequence restarts and the banner prints again.
The extra blank lines come from three sources: CR→CRLF at 04ce, the message's own `0a 0d`, and the CR printed at 004c.
The boot ROM emits no ESC sequences, so it is pure line output. Confirmed with TEK_IOTRACE8301 and -hsilog.

## 8086/8088 emulator
The board set is emulated and passes its diagnostic: see `notes/8086.md`. What concerns DOS/50:
- **The support disc (`8550_8086.IMD`, volume EMU.8086, 11-OCT-82)** has only a `VERSION2/` directory, for DOS/50 V2. By contrast the 8085 disc has both `VERSION1/` (a `MONITORS` and `DS[TAT]` for V1.x) and `VERSION2/`. Its contents:
  - `MONITORS` (13 KB) is a DOS/50 load module of **2650 code**: its jump table points at 5Bxx–5Fxx, the overlay area, and it holds the break messages "TRAP occurred -- old CS:IP SS:SP FLAGS" and "INT2 occurred". It is DOS/50's side of the 8086 emulator, not the board's firmware.
  - The command overlays `DS[] BK[] TRA[] SVC[] MAP[] MEM[] NOMEM[] MEMSP[] AL[] DEAL[] RD[] WRT[] SNDP[]` and `EMU*.INIT`.
- **`INSTALL2` uses V2 commands.** Its first line, `T ON`, gives "Error 13 Command not found" under V1.0, which then abandons the command file.
- **Installed by hand under V1.0's layout (`/8301/8086`), `SEL 8086` gives "Error 2D System dead – reboot or reselect"**, with no board fitted. (The board's kernel PROMs did survive: `notes/8086.md`.)
- **The 8086's TTA bus symbols** (TNIX 2.0's TTA help): `f` first fetch, `fs` subsequent fetch, `ir` I/O read, `iw` I/O write, `rd` memory read, `wt` memory write, `ht` halt, `lck` lock, `int` interrupt, `ia` interrupt acknowledge, `es` `ss` `cs` `ds` the segment in use, `bhe` bus high enable, `tst` test ("Example: b=cs wt, memory write to a code segment").
- **Bracketed names** (`ATT[RIBUTE]`, `DS[]`): DOS/50 applies the abbreviation only when looking up a command; a file path needs the full name (`COPY /VOL/X/BR[ACKET] CONO`). tekmato 0.2.1 creates such names (quote them in the shell: `'8301/8086/DS[]'`).

## Program memory boards (emulated in `tek8301::prog_phys`, `pm_read`/`pm_write`)
**Source:** 070-2976 section 7 (ports B8/B9) and section 11 (memory relocation, extended bank). **Checked by:** the memory diagnostic (Select mode 2, MEM.TST V1.4).

- **Two 32 KB boards.** The low board answers bus addresses 0000–7FFF, the high board 8000–FFFF.
- **Relocation** works when jumper J5175 is on and B8/B9 D4 = 0:
  - the bus address's A15–A12 index a 16 × 4-bit relocation RAM, whose output becomes the physical A15–A12;
  - so one 32 KB board covers the 64 KB bus space in 4 KB blocks, and blocks relocated to the other half answer nothing.
- **Loading the RAM:** writes go through a counter (D5 = 1 resets it). Reads return the entry at the counter and advance it: the static test writes 16 entries, then reads 16.
- **Reset** disables relocation *(inferred: a 32 KB system must boot)*.
- **Extended bank:** with the comparator in use (`-pm ext`, D6 = 0), a board answers only when A23–A16 equal its DIP switch (00).
- **An address no board answers reads 00.** The power-up test (diag ROM 0499) treats a bank reading 00 as not installed.
- **`-pm 32k`** fits only the low board, with J5175 on. MEM.TST then sizes the system as "PROGRAM MEMORY = 32K at 000000" and passes options 4 (relocation RAM static test, test 12) and 5 (relocation functional test, 13). Option 0 passes on both 32K and 64K systems.
- **The 8086/80186 board** drives the physical A19–A16 from its relocation RAM onto the extended address lines (`notes/8086.md`).
